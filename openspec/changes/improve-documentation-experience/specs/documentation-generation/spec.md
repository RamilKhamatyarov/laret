## MODIFIED Requirements

### Requirement: Markdown documentation layout

`doc generate --format md` MUST write one page per documented command at `{lang}/{group}/{command}.md`, a group index at `{lang}/{group}/index.md`, and a root index at `{lang}/index.md`, plus a single `mkdocs.yml` generated from one committed configuration template. Navigation MUST include Guide, Reference, Benchmarks and Changelog sections, with command groups nested under categorized Reference navigation. `--lang all` MUST emit every supported language. The command MUST report each written path and the total number of files. The site build MUST consume the generated configuration, not a second independently maintained configuration.

#### Scenario: Page tree
- **WHEN** documentation is generated for group `file` with command `create` in language `en`
- **THEN** `en/file/create.md`, `en/file/index.md`, `en/index.md`, and `mkdocs.yml` are written

#### Scenario: All languages
- **WHEN** the user passes `--lang all`
- **THEN** Markdown is generated for each supported language

#### Scenario: Single configuration authority
- **WHEN** the documentation site is built
- **THEN** its effective configuration is generated from the committed template, includes the four sections, and has no competing ignored configuration

## ADDED Requirements

### Requirement: Canonical branded site

The published site MUST use the absolute base URL `https://ramilkhamatyarov.github.io/laret/`, link the repository and the appropriate editable source from every content page, and supply a logo, favicon and accessible light/dark themes. Sitemaps and language alternates MUST contain only absolute URLs rooted at the real site base, never null placeholders.

#### Scenario: Metadata and header
- **WHEN** a page is built in either locale
- **THEN** its repository and source-edit links resolve to their intended destinations, and its sitemap and alternate URLs retain the site base path

#### Scenario: Navigation and error recovery
- **WHEN** a visitor navigates the reference or requests an unknown URL
- **THEN** the reference presents expandable categories rather than an always-expanded list of every group, and the error page offers localized search and a working home link

#### Scenario: Theme and content rendering
- **WHEN** a visitor switches theme or opens a page containing tables, admonitions, tabbed code, diagrams or linked code tabs
- **THEN** content remains legible, keyboard-operable and correctly rendered on desktop and mobile, with a persistent theme choice and named controls

### Requirement: Existing prose publication

The site MUST publish the existing benchmarks and managed-sidecar manifest content through reachable navigation. It MUST distinguish documented foundations from functionality not yet wired to the CLI. README links and assets MUST resolve both on GitHub and in the generated landing page, including fragments and repository-only destinations.

#### Scenario: Documentation links
- **WHEN** either existing prose page or a README relative link is followed in either context
- **THEN** the intended content is reached without a missing page or missing asset, and benchmark tables render as tables

### Requirement: Traceable benchmark visualization

Benchmark charts MUST be generated by the existing Python benchmark tooling from approved committed raw results, with labeled axes, units, target names, scenario boundaries and provenance. Chart data MUST reproduce source values without changing measurements or claims. Unsupported startup claims MUST NOT be inferred from concurrency measurements.

#### Scenario: Missing chart source
- **WHEN** no suitable raw results artifact is committed
- **THEN** chart acceptance remains blocked pending approval of an exact source; neither numbers nor an illustrative performance chart are invented

#### Scenario: Reproducible chart
- **WHEN** a chart is regenerated from its approved source
- **THEN** plotted values match the source, source caveats accompany it, and an accessible text/table equivalent is available

### Requirement: Clickable cross-references

Generated Markdown See Also entries MUST link to the correct relative command pages in the current locale. Validation MUST diagnose unknown targets and invalid local or cross-page fragments without rewriting author source files.

#### Scenario: Related command
- **WHEN** a valid command identifier occurs in See Also
- **THEN** its rendered link resolves from the current page to that command's page, including when group names differ

### Requirement: Read-only documentation checking

A check-only mode MUST validate command prose coverage, cross-references and orphaned prose without creating, changing or deleting files. It MUST report all detected problems with actionable source locations and exit nonzero for invalid coverage or references. Existing generation and non-strict fallback behavior MUST remain available.

#### Scenario: Missing source page
- **WHEN** a command lacks prose and check-only validation runs
- **THEN** validation fails and a before/after filesystem comparison finds no changed paths

#### Scenario: Clean source
- **WHEN** command coverage and all checked references are valid and no orphan exists
- **THEN** check-only validation exits zero without writing generated output

### Requirement: Reviewed command coverage

Every visible command MUST have committed reviewed prose stubs in English and Spanish. The ten priority commands MUST each have a purpose sentence, a realistic supported example and a valid cross-reference: doc generate, plugin install, pipe run, watch live, prompt select, config explain, new project, mcp serve, update run and completion interactive. CI MUST NOT create missing source stubs to satisfy coverage.

#### Scenario: Blocking publication gate
- **WHEN** priority content and coverage are complete and a new command subsequently lacks a source page
- **THEN** the blocking documentation check fails CI rather than silently using generated prose or an advisory failure

### Requirement: Accurate newcomer README

The README MUST remain an in-place evolution with valid emphasis, approximately ten linked feature groups, a short contents list, verified runtime/build requirements, separate CLI and library installation, live CI/release badges and an accessible appendix for relocated structure/details. CLI instructions MUST explain download selection and checksum verification for assets actually released.

#### Scenario: First installation
- **WHEN** a newcomer follows CLI instructions on a supported release platform
- **THEN** the documented artifact exists, its checksum can be verified, the executable starts, and JVM development requirements are not misrepresented as native-runtime requirements

#### Scenario: Existing material
- **WHEN** features or demos are condensed on the landing page
- **THEN** their substantive material remains reachable in linked sections, an appendix or a gallery unless deletion was separately approved

### Requirement: Real and cacheable demos

The landing page MUST show a real-command hero story covering project scaffolding, running the generated project, help and completion, with separate interactive-completion, prompt-selection, live-watch and plugin-install demos. Recordings MUST share consistent presentation and omit unnecessary idle time. A static social preview and nonanimated text alternatives MUST be provided.

#### Scenario: Supported recording
- **WHEN** a demo is rendered
- **THEN** commands really execute in a controlled terminal/workspace, plugin installation uses a repository-owned pinned fixture, and unsupported behavior fails visibly rather than being simulated

#### Scenario: Cache reuse and invalidation
- **WHEN** tapes and all rendering/execution inputs are unchanged and cached outputs exist
- **THEN** rendering is skipped and valid assets are restored

#### Scenario: Cache invalidation
- **WHEN** an input changes or a required asset is absent
- **THEN** affected recordings are rendered and validated rather than serving stale or missing outputs

### Requirement: Complete published locales

English and Spanish MUST both remain published. Spanish navigation, headings, descriptions, landing/guide prose and error recovery MUST be Spanish rather than silently falling back to English. Command identifiers, code, proper names and explicitly identified quoted source evidence MAY remain unchanged. General-purpose library prose fallback MUST retain its existing contract.

#### Scenario: Spanish release
- **WHEN** a Spanish site page is published
- **THEN** its navigation, framework headings and explanatory content are translated, its related links stay in the locale where equivalents exist, and reviewed content coverage prevents whole English pages leaking into Spanish

### Requirement: Contribution and trust guidance

The repository and site MUST expose contribution instructions, a release-based changelog, a verified private security-reporting path and issue/PR templates. Contribution guidance MUST cover build, tests, native compilation and documentation conventions. API reference and versioned docs MUST be explicitly deferred with reasons and reconsideration prerequisites.

#### Scenario: Verified project information
- **WHEN** a visitor reads release or security guidance
- **THEN** changelog entries trace to actual releases and security instructions use a verified private route; absence of such a route blocks publication of invented contact details

### Requirement: Sequential verified delivery

The eight phases MUST remain independently reviewable and proceed in order only after current-phase checks pass. Evidence MUST identify files and commands/tests or URLs, distinguishing local verification from deployed verification. Unavailable deployment evidence MUST be marked pending, not successful.

#### Scenario: Phase handoff
- **WHEN** a phase has failing local acceptance or an unresolved required approval
- **THEN** the next phase does not begin, and the blocker and existing passing evidence are recorded
