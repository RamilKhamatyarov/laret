# Concurrency and Parallel Execution Benchmarks

Laret measured against four other CLI stacks on the orchestration work a
framework does *after* start-up: fan-out scheduling, event coalescing, streaming
pipelines and cancellation under load. Cold-start numbers are a different
question and are not on this page.

This file is generated by `benchmarks/harness/render.py`. It is not generated
into `site/docs`, because `laret doc generate` overwrites that tree.

## Rules

- **No external I/O.** Payloads are CPU or memory bound.
- **Pinned and isolated.** Every process is pinned with `taskset`; each scenario
  finishes and releases its memory before the next begins.
- **Warmed up.** A discarded dry run precedes the timed runs.
- **Linux only.** Pinning and peak RSS (`/proc/<pid>/status` `VmHWM`) are
  Linux-specific, and numbers are not comparable across operating systems.
- **Native abstractions.** Where a framework has its own parallel dispatch or
  pipeline, that is what is measured.

## Scenario A - Parallel fan-out and fan-in

## Scenario B - Event storm

The CLI enters watch mode and a storm of events is fired into it. The framework
must filter, debounce and coalesce them into exactly one execution of the target
command. Coalescing is strict pass/fail.

Wall clock is mostly the storm's own designed quiet period, identical for every
target. *Settle* is the time from the last event to the coalesced run, and
*above debounce* is the part of it the framework adds on top of the window.

| Target | Settle | Above debounce | Wall clock | Peak RSS | Coalescing |
|---|---|---|---|---|---|
| Cobra | 150.5 ms | 0.5 ms | 453.7 ms | 5.8 MiB | pass |
| clap | 151.4 ms | 1.4 ms | 454.4 ms | 3.6 MiB | pass |
| picocli | 150.2 ms | 0.2 ms | 646.9 ms | 128.5 MiB | pass |
| Laret JVM | 151.6 ms | 1.6 ms | 831.9 ms | 164.8 MiB | pass |
| Laret native | 150.2 ms | 0.2 ms | 460.5 ms | 43.5 MiB | pass |

## Scenario C - Concurrent streaming pipeline

A three-stage pipeline with every stage live at once: stage one emits lines,
stage two filters and transforms concurrently, stage three aggregates a count.
This measures I/O multiplexing and whether the pipeline stays synchronised
without deadlocking, dropping lines or exhausting memory.

| Target | Wall clock | Overhead per line | Peak RSS | Lines correct |
|---|---|---|---|---|
| Cobra | 17.0 ms | 0.17 µs | 7.6 MiB | pass |

| Laret native | 28.6 ms | 0.29 µs | 41.6 MiB | pass |

## Reproducing

```bash
# Linux only.
benchmarks/harness/build.sh
python3 benchmarks/harness/harness.py --out results.json
python3 benchmarks/harness/render.py results.json > docs/benchmarks.md
```

CI does not gate on any timing. Pull requests run the scenarios once at reduced
scale and assert only the deterministic properties. The full five-target suite
runs nightly and uploads `results.json` and this table as artifacts.
